# 네트워크 아키텍처

## 전송 계층

- Godot `ENetMultiplayerPeer`, UDP 기본 포트 7777
- 서버 1명 + 원격 클라이언트 1명(`MAX_CLIENTS = 1`)
- 호스트 PC가 서버와 흑돌 플레이어를 겸한다.
- 참가자는 백돌이며 IPv4로 직접 접속한다. Tailscale을 사용할 때 `100.x.x.x` 주소를 입력한다.
- 방 코드, NAT 우회, 릴레이 서버는 구현하지 않았다. Tailscale이 두 PC 사이의 VPN 경로를 제공한다.

## 권한 모델

호스트만 물리와 규칙의 최종 상태를 변경한다. 클라이언트가 보내는 패킷은 다음 세 종류의 명령뿐이다.

1. `request_shot(piece_id, pull_vector, sequence)`
2. `request_augment_choice(selection_stage, augment_id, sequence)`
3. `request_active_skill(augment_id, target_ids, board_position, sequence)`

호스트는 송신 peer를 실제 플레이어 ID에 매핑하고, 단조 증가 sequence, 현재 선택 단계 ID, 단계별 제안 목록, 중복 선택 여부, 최대 3개 제한, 현재 턴, 상태, 소유권, 알 ID, 드래그 한계, 증강 보유·쿨다운·대상 소유권을 검증한다. 좌표, 승자, 소유권을 클라이언트가 직접 확정하는 RPC는 없다.

공동 라운드 수와 양쪽 행동 완료 플래그는 호스트만 변경한다. 3·6라운드 보상 시 호스트는 같은 단계 ID로 각 플레이어에게 독립 후보를 보내고 두 선택을 임시 보관한다. 양쪽 요청이 모두 검증된 뒤 두 증강을 적용·동기화하고 reliable 완료 RPC로 다음 라운드를 연다. 선택 중에는 발사/액티브 입력과 정지 상태의 반복 스냅샷 전송을 막는다.

## 상태 동기화

- 호스트가 20Hz로 `unreliable_ordered` 스냅샷을 전송한다.
- 스냅샷에는 게임 상태, 현재 턴, 공동 라운드와 행동 완료 플래그, 승자, 알의 ID·소유자·위치·속도·물리/변신 상태, 임시 벽 ID·위치·회전·남은 시간, 필드 상태와 증강 런타임 상태가 포함된다.
- 알 상태는 필드명 없는 고정 배열로 압축해 일반 3~5알 대전에서 ENet MTU 아래를 유지한다.
- 클라이언트의 `RigidBody2D`는 `freeze` 상태이며 받은 위치를 보간한다. 충돌·탈락·턴 종료를 로컬에서 확정하지 않는다.
- 증강 제안과 획득, 월드 시작, 투사체 연출은 reliable RPC로 보낸다. 분열 알과 임시 벽, 변신, 필드 및 특수 승리는 권위 스냅샷으로 수렴한다.

## 로비

호스트가 시작 알 수 3/4/5를 정한다. 양쪽 준비 상태가 참이고 참가자가 연결된 경우에만 호스트의 시작 버튼이 활성화된다. 최초 증강 후보는 호스트 RNG가 각 플레이어별로 생성한다. 로컬 화면에는 자신의 후보만 표시된다.

## 오류 처리

- IPv4/포트 입력을 생성 전에 검증한다.
- ENet 연결 실패와 서버 종료는 메뉴에 오류를 표시한다.
- 참가자가 나가면 호스트는 로비로 돌아가고 준비 상태를 해제한다.
- 세 번째 연결은 ENet의 최대 클라이언트 수와 추가 peer 검사로 거절한다.
- 중복·과거 sequence, 턴 외 발사, 다른 소유자의 알, 존재하지 않는 알, 허용 범위 밖 드래그, 미보유/쿨다운 증강과 잘못된 대상은 무시한다.

## 현재 한계

- 재접속, 관전자, 호스트 이전, NAT traversal, 암호화된 계정 인증은 없다.
- 순간적인 보드 선 이펙트와 기차 예고선 일부는 클라이언트에서 별도 연출 RPC가 없어 스냅샷 결과만 보일 수 있다. 투사체, 생성 알, 벽 및 실제 물리 결과는 동기화된다.
- 인터넷 품질에서의 지터 버퍼와 대역폭 적응은 후속 과제다.
